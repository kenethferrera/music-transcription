PROJECT IMPLEMENTATION PROMPT AI-POWERED MUSIC TRANSCRIPTION WEB
APPLICATION Demucs + MuScriptor Large + External STT API + GHCR

ROLE Act as a senior full-stack engineer, AI/ML engineer,
audio-processing specialist, and DevOps engineer. Implement a complete,
maintainable web application that converts uploaded songs into
synchronized multitrack MIDI, karaoke MIDI, full-score PDF, and
lead-sheet PDF.

Do not stop at architecture documents or mockups. Build and test a
working application incrementally. Do not fabricate model outputs, APIs,
capabilities, or progress.

============================================================ 1. PROJECT
GOAL ============================================================

Users must be able to: - Upload a complete song (MP3, WAV, FLAC, and
practical FFmpeg-supported formats). - Separate vocals, drums, bass, and
other audio using Demucs. - Recognize lyrics using a configurable
external STT API. - Transcribe musical notes using MuScriptor Large. -
Organize notes into instrument tracks where the model output supports
this. - Estimate chords, tempo, key, and time signature using non-AI
signal-processing/music-theory methods. - Edit notes, lyrics, chords,
and instrument assignments. - Export: 1. Multitrack MIDI (.mid) 2.
Karaoke MIDI (.kar) 3. Full-score sheet music PDF 4. Lead-sheet PDF

The original audio is an input and intermediate reference. Do not embed
the original MP3 in MIDI or KAR exports.

STRICT MODEL POLICY: Use only these AI model families: 1. Demucs for
source separation. 2. MuScriptor Large for musical transcription.

Use an external STT API for lyrics. Do not install Whisper, Whisper.cpp,
YourMT3/YourMT3+, UVR, RMVPE, Basic Pitch, Omnizart, or any other AI
separation/transcription model.

Non-AI signal processing, music theory, MIDI processing, lyric alignment
algorithms, and ordinary software libraries are permitted. If another AI
model appears technically necessary, explain why and request approval
before integrating it.

============================================================ 3. CLOUDFLARE R2 OBJECT STORAGE
============================================================

Cloudflare R2 is the required persistent object storage for production.
Use its S3-compatible API so the backend can use boto3 or another
maintained S3-compatible SDK.

Configuration:
- R2_ACCOUNT_ID
- R2_BUCKET_NAME
- R2_ACCESS_KEY_ID
- R2_SECRET_ACCESS_KEY
- R2_ENDPOINT_URL=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
- R2_REGION=auto

Read all values from environment variables or the deployment secret
manager. Never commit credentials, print them in logs, expose them to the
browser, or bake them into Docker images. Provide a safe .env.example
containing placeholders only.

Implement an object-storage abstraction (for example, StorageService)
so application code does not depend directly on boto3 calls. The
production adapter must target R2. A MinIO adapter may be included for
local development and automated tests, but it must not silently replace
R2 in production.

Object organization:
- Use generated, non-guessable object keys scoped by user and project.
- Keep original uploads, Demucs stems, temporary/intermediate artifacts,
  canonical arrangement data, and exports in clearly separated prefixes.
- Store object keys and metadata in the application database; do not use
  public URLs as the database's source of truth.
- Keep buckets private by default.
- Validate ownership and authorization on every upload, read, and
 delete request.
- Record content type, byte size, checksum where practical, creation
  time, project ID, artifact type, and processing/model version.

Browser transfer:
- Prefer backend-generated, short-lived presigned PUT URLs for direct
  browser-to-R2 uploads and presigned GET URLs for authorized downloads.
- The backend must authenticate the user and authorize the project
  before issuing any URL.
- Use short expiry times appropriate to the operation; treat every
  presigned URL as a bearer credential.
- Restrict upload object keys to server-generated paths and bind the
  expected content type where supported.
- Configure bucket CORS only for the exact application origins and
  required methods/headers.
- After upload, verify the object exists and validate size/type before
  enqueueing expensive GPU processing.
- Design large-file uploads carefully. Check current R2 multipart-upload
  support and SDK behavior before implementing resumable/multipart flows;
  do not assume browser HTML form POST uploads are supported by R2's
  presigned URL mechanism.

Worker access:
- GPU and CPU workers should access R2 using server-side credentials
  with least-privilege bucket-scoped permissions.
- Workers should download inputs to bounded temporary scratch space,
  process them, upload outputs, and clean local temporary files reliably.
- Make transfers retryable and idempotent. Avoid downloading the same
  large artifact repeatedly when a local cache is safe and available.
- Do not assume a GPU worker's local disk is durable.

Retention and deletion:
- Define configurable retention rules for temporary intermediates,
  failed-job artifacts, original uploads, and user-requested exports.
- Do not automatically delete user projects or final exports without a
  clearly documented policy and user-visible behavior.
- Support project deletion by deleting associated R2 objects and
  database records safely, with retry/reconciliation for partial failure.
- Use R2 lifecycle rules only for prefixes whose retention behavior is
  explicitly understood; avoid broad rules that could delete user data.

Testing and operations:
- Add an R2 connectivity/permissions health check that does not expose
  secrets.
- Test upload, download, head/stat, delete, presigned URL generation,
  CORS, large-file behavior, retries, and authorization boundaries.
- Document bucket creation, API-token creation, least-privilege
  permissions, CORS configuration, lifecycle setup, and deployment
  secrets.
- Keep storage provider configuration separate for local, staging, and
  production environments.

Official documentation to verify during implementation:
- https://developers.cloudflare.com/r2/get-started/s3/
- https://developers.cloudflare.com/r2/api/s3/presigned-urls/
- https://developers.cloudflare.com/r2/buckets/object-lifecycles/

============================================================ 4. DEMUCS
SOURCE SEPARATION
============================================================

Official repository: https://github.com/facebookresearch/demucs

Use an appropriate official pretrained Demucs checkpoint. Standard
four-stem output should be: - Vocals - Drums - Bass - Other

Requirements: - Preserve the original song timeline and duration as
closely as possible. - Save separated stems as WAV. - Maintain
consistent sample-rate and channel handling. - Handle long songs without
exhausting GPU memory. - Use chunking only where supported and
reconstruct chunk boundaries without timing gaps. - Store stems in
persistent object storage. - Provide stem previews in the web
interface. - Record processing settings, model/checkpoint version, and
errors. - Allow failed separation jobs to be retried.

IMPORTANT LIMITATION: Standard four-stem Demucs does not independently
separate piano, guitar, strings, and every other instrument. Do not
label the four stems as individual instruments or claim that they
provide isolated piano and guitar tracks.

============================================================ 4.
MUSCRIPTOR LARGE TRANSCRIPTION
============================================================

Model: https://huggingface.co/MuScriptor/muscriptor-large

Use MuScriptor Large as the only automatic musical-note transcription
model.

Before implementing inference: 1. Inspect the official model page and
source repository. 2. Locate and inspect the actual checkpoint and
documented inference code. 3. Verify supported audio formats, sample
rates, channels, and duration limits. 4. Verify what note, timing,
instrument, confidence, and velocity information is actually returned.
5. Verify GPU/VRAM requirements and dependencies. 6. Verify the model
and checkpoint license and redistribution restrictions. 7. Record any
missing capabilities or implementation risks.

Do not invent an inference API or assume undocumented functionality.
Implement the actual documented inference path.

Where supported, extract: - Instrument identity/category - MIDI pitch -
Note onset - Note offset/duration - Velocity - Confidence - Track
association

Normalize model output into the application’s shared music
representation. Do not fabricate unavailable values. If velocity is
missing, use a documented configurable default or a clearly identified
non-AI estimation method. If instrument identity is uncertain, preserve
uncertainty and allow manual reassignment.

Transcription strategy: 1. Run Demucs on the original song. 2. Run
MuScriptor Large on the original mixed audio. 3. Evaluate MuScriptor on
relevant separated stems where supported. 4. Benchmark original-mix and
stem-based transcription. 5. Compare and reconcile results. 6. Remove
duplicate/conflicting note events carefully. 7. Assign notes to
instrument tracks only when supported by evidence. 8. Preserve the
original song timeline.

Do not assume that running MuScriptor on every stem improves accuracy.
Benchmark first and avoid unnecessary GPU work. Do not shift stems
independently.

IMPORTANT LIMITATION: Demucs four-stem output does not isolate piano and
guitar separately. MuScriptor’s actual instrument-identification
abilities must be verified. Do not promise perfect
instrument-by-instrument transcription. Mark uncertain assignments and
allow manual correction.

============================================================ 6. EXTERNAL
STT API FOR LYRICS
============================================================

Use an external speech-to-text API for lyric recognition. Do not install
a local STT model.

Implement a provider adapter in the backend so the STT provider can be
changed without rewriting the pipeline.

Default input: Demucs vocal stem. A configurable comparison against the
original mix may be added if testing supports it.

Requirements: - API key supplied through environment
variables/secrets. - Request timeout and bounded retry handling. -
Audio-size and provider duration-limit handling. - Response validation
and provider-specific adapters. - Normalize results into a common lyric
format. - Preserve word/segment timestamps when returned. - Clearly
represent missing or coarse timestamps. - Allow manual lyric correction.

Do not assume every STT provider returns word-level timestamps. STT
recognizes words; it does not identify musical pitches.

LYRIC-TO-NOTE ALIGNMENT: Implement a separate non-AI alignment component
that associates recognized words/syllables with vocal note events.
Consider: - Word timestamps - Note onset and offset - Syllable
segmentation - Sustained vowels - Melisma (one syllable across multiple
notes) - Multiple syllables within a phrase - Gaps and repeated words -
Vocal ornaments

Do not assume one word equals one note. Do not fabricate precise
syllable timing when the STT response lacks it. Preserve uncertainty and
provide manual editing.

============================================================ 7. VOCAL
MELODY ============================================================

Use MuScriptor Large’s actual supported transcription output for vocal
melody notes where possible.

Do not add RMVPE or another AI pitch model.

Requirements: - Identify vocal-related notes only where the model
supports it. - Preserve pitch and timing. - Associate lyrics with notes
using the alignment component. - Allow manual note editing. - Mark
uncertain or unavailable melody data clearly.

If MuScriptor cannot reliably distinguish vocal melody from
accompaniment, do not fabricate a vocal melody. Investigate non-AI
signal-processing options or expose the limitation for manual
correction.

============================================================ 8. MUSICAL
ANALYSIS ============================================================

Implement non-AI algorithms for: - Chord estimation - Key estimation -
Tempo/BPM estimation - Time-signature estimation where feasible - Beat
and bar positions - Tempo changes where detectable

Use transcription and audio features as evidence. Store
confidence/uncertainty. Allow manual correction. Do not assume all songs
have constant tempo or meter, and do not present uncertain analysis as
ground truth.

============================================================ 9. SHARED
INTERNAL MUSIC REPRESENTATION
============================================================

Create one canonical internal arrangement representation as the source
of truth for every export.

It should include: - Project metadata and original duration - Sample
rate and timing reference - Tempo map - Time-signature map - Key
information - Chord events - Instrument tracks - MIDI note events -
Vocal notes - Lyrics and timestamps - Instrument assignments -
Confidence/uncertainty - Source stem references - Manual edit history
where practical

Each note event should support: - Track ID - Instrument name/MIDI
program where known - Pitch - Start time - End time/duration - Velocity
when available - Confidence when available

Use a consistent high-resolution timing representation. Keep every track
aligned to the original audio timeline. Generate MIDI, KAR, and MusicXML
from this same representation; do not create separate inconsistent
pipelines.

============================================================ 10. MIDI
EXPORT ============================================================

Generate a standards-compliant Standard MIDI File Type 1.

Create separate tracks where data is available: - Vocals - Piano -
Guitar - Bass - Drums - Other identified instruments - Optional
chord/marker track

Include where available: - Note-on and note-off events - Velocity -
Program changes - Tempo events - Time-signature events - Key-signature
metadata where supported - Track names - Appropriate percussion channel
assignments

Do not invent instrument identities or velocities. Use documented
defaults only when necessary. Do not embed original audio.

Reopen and validate generated MIDI files in tests.

============================================================ 11. KARAOKE
MIDI EXPORT (.KAR)
============================================================

Generate a karaoke MIDI file using appropriate MIDI lyric meta-events.

Requirements: - Synchronized lyric text events - Vocal melody notes -
Word/syllable timing to the accuracy supported by alignment - Tempo and
timing metadata - Other arrangement tracks where appropriate -
Consistent MIDI timing

Do not place all lyrics at the beginning. Do not embed original audio.
Test compatibility with common karaoke MIDI players and validate the
lyric event sequence.

============================================================ 12. SHEET
MUSIC PDF EXPORT
============================================================

Use MusicXML as the shared notation format. Generate MusicXML from the
canonical internal arrangement. Render using Verovio or LilyPond.
Inspect actual rendered PDFs.

FULL SCORE: Include available, transcribed parts: - Vocal melody with
lyrics - Piano grand staff where appropriate - Guitar - Bass -
Drum/percussion notation - Other identified instruments

Include appropriate clefs, key/time signatures, tempo, bar lines, note
values, rests, ties/dots where justified, chord symbols where
appropriate, lyrics, instrument labels, page numbers, and readable
spacing.

Do not create empty staves for unavailable parts. Do not invent notes to
fill measures. Handle uncertain data honestly.

LEAD SHEET: Include: - Main vocal melody - Lyrics aligned below notes -
Chord symbols - Key signature - Time signature - Tempo - Bar lines -
Readable, compact layout

Validate MusicXML and inspect PDF output for notation readability.
